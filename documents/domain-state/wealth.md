## Key Design Decisions (ADRs)

- `CreateAccountCommand` has **8 fields** as of the `currency` field addition (contract-consolidation pass, confirmed 2026-07-06): `accountName`, `accountType`, `institutionName`, `currency`, `openingBalance`, `creditLimit`, `interestRate`, `emiAmount` — was 7 before `currency` was added. `profileId` is passed separately: `createAccount(UUID profileId, CreateAccountCommand cmd)`. Never add `profileId` back into the command (SonarQube S107 — too many constructor params).
- **(2026-07-09, Sonar S107 cleanup) New `UpdateAccountCommand`/`UpdatePhysicalAssetCommand` records (`ports/input/`)** bundle the partial-update payload for `AccountUseCase.updateAccount`/`PhysicalAssetUseCase.updateAsset` — both methods had grown to 8/9 loose parameters and tripped Sonar S107. Follows the exact `UpdateAccountClassificationCommand` precedent: `id`/`profileId` stay as separate leading parameters on the use-case method (identity/scope, never bundled into the command), the command record carries only the update fields (`UpdateAccountCommand`: accountName/openingBalance/creditLimit/interestRate/emiAmount/isActive; `UpdatePhysicalAssetCommand`: assetName/make/model/metadata/isActive/currentValue/valuationDate). `AccountResource`/`PhysicalAssetResource` build the command from the existing wire-level `UpdateAccountRequest`/`UpdatePhysicalAssetRequest` DTOs — no contract/OpenAPI change, HTTP request/response shapes are untouched. Any future field added to either partial-update path should go on the command record, not as a new loose parameter.
- Dedup key is **4 fields**: `(account_id, txn_date, amount, txn_type)` — description excluded to handle cases where the same transaction has slightly different narrations across files. `TransactionRepository.existsByDeduplicationKey()` implements exactly this 4-field check and is called only from the CSV upload path (`StatementUploadService`). **Correction (2026-07-06):** the DB `uq_transaction_dedup` constraint is *not* actually a safety net for this rule — it additionally requires `description` to match exactly, which is a narrower/stricter condition than the 4-field business key, so it does not backstop the case it exists to cover (two rows with the same account/date/amount/type but differently-worded narration are exactly what the 4-field rule treats as duplicates, but the 5-field DB constraint would let them both insert). See Open Issues for the full analysis and recommended fix (not implemented this pass).
- Same-file duplicate rows are disambiguated by appending ` #2`, ` #3` etc. to the description. These variants bypass the cross-file dedup check (tracked in `insertedThisBatch` set in `StatementUploadService`).
- `CsvParseException` extends `BadRequestException` and lives in `adapters/services/` — it carries a machine-readable `errorType` and `missingColumns` list so the upload service can write a structured `upload_error_log` row before re-throwing.
- `StatementUploadUseCase.uploadStatement()` returns `UploadResult` (not `StatementUpload`) — wraps the upload entity with `insertedCount` and `List<SkippedRow>`.
- No SQL ENUMs anywhere — all discriminators are `VARCHAR` enforced at the OpenAPI contract layer.
- All DB queries filtered by `profile_id` in the adapter layer only.
- **(2026-07-09) Physical-asset value counts toward `WEALTH_NET_WORTH` but explicitly NOT toward `computeTotalBalance()`/goal progress.** `ProjectionCalculationEngine.computeNetWorth()` sums active physical assets' `current_value` into the profile's net worth; `computeTotalBalance()` (which backs `computeGoalProgress()` and, transitively via each member's call, `computeFamilyNetWorth()`) deliberately does not. Rationale: real estate/gold are illiquid, and goals like Freedom Runway are specifically about liquid/liquid-adjacent capital per `Financial_Data.md`'s own liquidity tiering — blending in illiquid value there would silently distort those goals. This means `WEALTH_NET_WORTH` (per-profile) and `WEALTH_NET_WORTH_FAMILY` (household rollup, ADR-017) can diverge from each other by exactly the physical-asset value — this divergence is intentional, not a bug, until/unless a future pass decides physical assets should roll up into the family total too (not decided here).
- **(2026-07-09) Mutual funds are modeled one `account` row per fund, not one aggregate row per person — no schema change.** Confirmed this fits the existing "1 row = 1 real instrument" pattern every other account type already follows (one row per bank account, one row per loan, etc.) — just a data-entry convention using the existing `MUTUAL_FUND` account type per fund, not a new field or table. `account.emi_amount` can be reused as "SIP amount" for a recurring monthly mutual-fund investment (same recurring-monthly-debit shape as a loan EMI) — cosmetic naming smell (column name is loan-specific), not renamed in this pass.
- **`StatementCsvParser` header-row detection (2026-07-09, real-file hardening): the header row is now located by scanning**, not assumed to be `lines.get(0)` — scan up to 50 lines for the first one where `detectColumns` succeeds; lines before it are discarded as preamble (real bank exports, e.g. Kotak, prepend account-metadata lines before the actual header). If no line in the scanned range is a valid header, line 0 is re-attempted so the thrown `CsvParseException` still carries the original, most-informative error — preserves prior behavior for genuinely malformed CSVs.
- **`StatementCsvParser` amount-layout precedence (2026-07-09): split debit/credit > Amount+indicator (Dr/Cr) > signed single amount.** The Amount+indicator layout (unsigned `Amount` column + separate `Dr / Cr` column, seen in Kotak) is new; when a file has two `Dr / Cr`-shaped columns (one qualifying Amount, one qualifying Balance — a real Kotak trait), leftmost-header-match-wins correctly binds to Amount's own indicator since it appears first in the row — a real, position-dependent assumption, not obvious from the code alone, flagged in a comment at `INDICATOR_HEADERS`.
- **`StatementCsvParser` date-column selection (2026-07-09) is priority-based, not leftmost-position-based** — the only column detected this way. `DATE_HEADERS` is iterated in priority order (`value date`/`value dt` first, then `transaction date`/`txn date`/`date`/`posting date`) and the first candidate matching *any* header wins, because a real file (Kotak) has both a `Transaction Date` (embedded timestamp, can differ on weekend/holiday postings) and a `Value Date` column, and the bank's own statement footer recommends Value Date for reconciliation — user-confirmed product decision. All other columns (description/debit/credit/amount/indicator/reference) keep leftmost-header-match-wins.
- **`StatementCsvParser.ParsedRow` carries an optional `referenceNumber()`** (from `Chq./Ref No.`/cheque/UPI-ref-shaped columns via `REFERENCE_HEADERS`) — unlike date/description/amount, a missing reference column is not an error. `StatementUploadService.uploadStatement()` threads it into `Transaction.create(...)`'s `metadata` map as `{"reference_number": ...}` when non-blank, `null` otherwise — no schema/contract change needed, `transaction.metadata` JSONB already round-trips arbitrary string keys.
- Future bank-format additions should follow the same pattern established here: extend the relevant `*_HEADERS` candidate list; only add priority-based (vs. leftmost-wins) detection logic if a single file has two competing valid headers for the same field, as Kotak did for date.

## v1.0 Retrospective — Domain Knowledge Refresh & Simplification Review (2026-07-06)

Scope: full re-read of `domain/`/`ports/`/`adapters/`, the live Flyway migration, `wealth.yaml`, and `web/src/pages/Wealth/` against this file, ahead of v1.0 planning. Product owner framing: "no new developments — time to retrospect and simplify, haven't gone live in production." **Documentation-only pass — no code changes made.** The schema-table and account-type corrections above, and the three verified-but-unfixed issues (dedup mismatch, amount-validation divergence, profile_id enforcement gap) in Open Issues, are the concrete output of this pass.

**Is Epic 8 (formula goals, EMI arbitrage, liquidity tiers, growth projections) genuinely load-bearing, or speculative complexity to trim before v1.0?** Developer's-eye view, largely agreeing with business-analyst's recommendation: **keep 8.1/8.2/8.4/8.5/8.6 as-is; don't retroactively build 8.3.** This isn't speculative complexity — it replaces a real, already-existing manual Python/markdown workflow the product owner ran before this system existed, every piece that shipped is exercised by tests at its own layer, and it's wired into the Dashboard the product owner actually looks at (Family Net Worth, EMI tracking, liquidity tiers, formula goals, validation banner). Just as tellingly, the product owner and business-analyst showed real restraint building it: no generalized formula engine, no auto-categorization rules engine, no per-bank CSV format registry were built speculatively — all three were explicitly deferred or declined (`OpenQuestions.md` Q15, Q24; the Phase 2 header-list non-extension) rather than over-built ahead of need. That's the discipline that keeps an epic like this from becoming the kind of complexity a retrospective should flag. UC 8.3 is correctly the piece left unbuilt: it's the most purely-advisory tier of the epic (alerts, not core net-worth/EMI math), and its inputs are the ones the domain doesn't cleanly own — `REQUIREMENTS_wealth_domain.md` itself flags household income (needed for the 30-70 Target check that UC 8.3's budget-cap logic depends on) as "not a wealth-domain-derivable figure." Deferring UC 8.3 isn't scope-cutting, it's deferring the one piece that was already blocked on an unresolved cross-domain/income question.

**What I'd actually simplify before v1.0 isn't epic scope — it's the `metadata JSONB` access pattern Epic 8 leans on.** `account.metadata`, `transaction.metadata`, and `physical_asset.metadata` all flatten loan terms, liquidity tier, purpose tag, joint owners, and category into `Map<String,String>`, and every consumer (`AccountService.getAmortization()`, the gateway's `computeEmiTracking`/`computeLiquidityTiers`/`computeGrowthProjection`/`computeFormulaGoals`) hand-rolls its own `new BigDecimal(str)` / `LocalDate.parse(str)` / `Integer.parseInt(str)` parsing inline, with no shared validation at write time — a typo'd or malformed metadata value fails at *read* time with an unchecked parse exception, not at the `PATCH /classification` call that wrote it. This was a reasonable, deliberate v0.1 choice (schema-less flexibility for sparse per-account data was an explicit early requirement — see `REQUIREMENTS_wealth_domain.md` v0.1 Epic 1), but by Epic 8 Phases 3-4 this JSONB blob is carrying real typed business config (loan principal/tenure/rate, policy thresholds), not just sparse optional metadata. That's the part worth tightening if there's appetite for a v1.0 cleanup task — e.g., a small shared `LoanMetadata.parse(Map<String,String>)`-style value object at the point where `AccountService.getAmortization()` currently does its three inline parses — separate from, and more concrete than, any question of trimming Epic 8's feature scope.

**Two smaller findings worth a v1.0-planning look**, beyond what's already in Open Issues: (1) `CreateAccountCommand` growing from 7 to 8 fields with the `currency` addition is fine today, but it's now one field away from the point where the existing "never add profileId back in, Sonar S107" ADR would also start applying pressure against adding a 9th — if EMI/loan fields keep growing on this record instead of moving into a nested value object, this record is worth revisiting before it does. (2) The `AccountType` enum drift found here (real enum has 10 values; `REQUIREMENTS_wealth_domain.md` v0.2 and `Accounts.js` both still show the old 7-value set with `INVESTMENT`) suggests account-type changes have happened at least once without a corresponding sweep of every reference — worth a lightweight process note (e.g., "grep for the enum name across contract/domain-state/frontend when adding an account type") rather than a code fix.
